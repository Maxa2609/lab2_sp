# Лабораторна робота №2: аналіз продуктивності програми

Досліджувана програма: множення двох квадратних матриць 1024x1024 (тип `double`), три вкладені цикли (`mm.c`).
Порівнюються дві збірки: `-O0` (без оптимізації) та `-O3 -march=native` (з оптимізацією та векторизацією AVX2).

**Відео-захист:** ПОСИЛАННЯ_НА_YOUTUBE

## Середовище

- Процесор: Intel Core i5-10500H (підтримує AVX2, AVX-512 немає)
- ОС: Ubuntu (live USB), нативний Linux (у віртуальній машині та WSL не працюють `perf` і лічильники енергії RAPL)
- Інструменти: `gcc`, `perf`, `/usr/bin/time`, [FlameGraph](https://github.com/brendangregg/FlameGraph), Python 3

## Збірка

    gcc -O0 -g -fno-omit-frame-pointer mm.c -o mm0
    gcc -O3 -march=native -g -fno-omit-frame-pointer mm.c -o mm3

Ключ `-g` додає символи для профілювальника, `-fno-omit-frame-pointer` зберігає frame pointer, щоб `perf` бачив стек викликів.
Обидві версії виводять однаковий результат (`88954368.000000`), отже оптимізація не змінила поведінку програми.

## 1. FlameGraph (п. 1, 4.3)

Побудова:

    git clone https://github.com/brendangregg/FlameGraph
    sudo perf record -F 999 -g ./mm0
    sudo perf script | ./FlameGraph/stackcollapse-perf.pl | ./FlameGraph/flamegraph.pl > mm0.svg

Те саме для `mm3`. `perf record` семплує стек 999 разів на секунду, `perf script` виводить стеки текстом,
`stackcollapse-perf.pl` згортає однакові стеки в рядки з лічильниками, `flamegraph.pl` малює SVG.

Інтерпретація:

- Ширина блока дорівнює частці процесорного часу, висота є глибиною стека викликів (знизу вгору: `_start` -> `main` -> `multiply`).
- Практично весь час займає функція `multiply` (~99.5% до оптимізації, ~97% після). Це гаряча точка програми.
- Над `multiply` немає інших блоків: вона сама виконує цикли і нічого не викликає.
- Тонкі стовпчики по краях це виклики ядра (обробка page fault при першому доступі до пам'яті).
- Після оптимізації блок `init` став помітним зліва. FlameGraph показує частки, а не абсолютний час: `multiply` скоротилась, а час `init` лишився тим самим.
  Абсолютне прискорення видно з кількості семплів (блок `all`): ~3000 для `mm0` і ~200 для `mm3`.
- У стеку `mm3` не видно кадра `main`. Це особливість розгортання стека в оптимізованому коді, на висновки вона не впливає.

## 2. Статистика виконання (п. 2, 4.2)

### 2.1 `/usr/bin/time -v`

    /usr/bin/time -v ./mm0 2> time_mm0.txt

| Показник | `-O0` | `-O3 -march=native` |
|---|---|---|
| Використання CPU | 99% | 99% |
| Максимальна пам'ять (RSS) | ~26 МБ | ~26 МБ |
| Major page faults | 0 | 0 |
| Minor page faults | ~8270 | ~8270 |
| Swaps, операції з диском | 0 | 0 |

Програма повністю завантажує одне ядро і не чекає на диск чи своп. Пам'ять (~26 МБ = три масиви по 8 МБ плюс службова) однакова
до і після оптимізації: змінюється не обсяг даних, а спосіб їх обробки.

### 2.2 `perf stat -d`

    sudo perf stat -d ./mm0 2> stat_mm0.txt

| Показник | `-O0` | `-O3 -march=native` | Зміна |
|---|---|---|---|
| Час (elapsed) | 3.058 с | 0.208 с | у 14.7 раза швидше |
| Цикли процесора | 12.78 млрд | 0.86 млрд | у 14.8 раза менше |
| Інструкції | 43.98 млрд | 1.11 млрд | у 39.5 раза менше |
| IPC (інструкцій за такт) | 3.4 | 1.3 | нижче |
| Розгалуження (branches) | 1.09 млрд | 0.14 млрд | у 7.7 раза менше |
| L1-dcache-load-misses | 139 млн | 138 млн | без змін |
| Частка L1-промахів | 1.0% | 33.3% | вища |
| Page faults | 8255 | 8257 | без змін |

Висновки:

1. Основна причина прискорення: інструкцій у ~39 разів менше. Векторні інструкції обробляють по 4 числа `double`, а змінні лежать у регістрах, а не в стеку.
2. IPC впав, але це не суперечність. Швидкість визначається загальною кількістю тактів, а їх у ~15 разів менше. У `-O0` багато простих інструкцій
   (звернення до стека), які добре виконуються паралельно, тому IPC високий. У `-O3` інструкцій мало, але програма частіше очікує дані з пам'яті.
3. Кількість L1-промахів однакова, бо шаблон доступу до пам'яті не змінився. Частка промахів виросла, бо загальна кількість звернень до пам'яті
   зменшилась приблизно в 30 разів. Тобто оптимізована програма обмежена пам'яттю (memory-bound), і її можна прискорити блочним множенням матриць.
4. Відсотки в дужках у виводі означають, що `perf` по черзі перемикає лічильники, тому значення наближені.

### 2.3 `perf record` та `perf report`

    sudo perf record -g ./mm0
    sudo perf report --stdio --no-children -g none

| Функція (Self) | `-O0` | `-O3 -march=native` |
|---|---|---|
| `multiply` | ~99.5% | ~97.2% |
| `init` | ~0.1% | ~0.2% |
| Функції ядра (page faults, виділення пам'яті) | ~0.3% | ~2.6% |
| Кількість семплів | ~12 000 | ~1 300 |

Колонка Self показує час у самій функції (Children додає ще й час викликаних функцій). Частка ядра зросла після оптимізації, бо
абсолютно ці витрати ті самі, а `multiply` скоротилась. Кількість семплів теж підтверджує прискорення.

## 3. Енергоспоживання (п. 3, 4.4)

Енергію виміряно лічильниками RAPL процесора Intel через `perf` (`power/energy-pkg/` для процесора, `power/energy-ram/` для пам'яті).

    sudo perf stat -a -e power/energy-pkg/,power/energy-ram/ -r 5 ./mm0

`-a` означає вимірювання всієї системи, `-r N` повторює запуск N разів і усереднює результат. Усі заміри виконує `measure.sh`:
спочатку 5 с простою (`sleep 5`), потім `mm0` (5 запусків) і `mm3` (20 запусків). Розрахунок виконує `energy_calc.py`.
Заміри зроблено окремо від запису екрана, щоб запис не спотворював результат.

**Потужність простою:** 2.43 Вт (процесор), 0.83 Вт (пам'ять).

| | `-O0` | `-O3 -march=native` | Зміна |
|---|---|---|---|
| Час | 2.788 с | 0.186 с | у 15.0 раза швидше |
| Енергія процесора (pkg) | 64.24 Дж | 4.82 Дж | |
| Енергія пам'яті (ram) | 2.65 Дж | 0.26 Дж | |
| **3.1 Система (pkg + ram)** | **66.89 Дж** | **5.08 Дж** | у 13.2 раза менше |
| **3.2 Лише програма** | **57.47 Дж** | **4.37 Дж** | у 13.2 раза менше |
| Середня потужність процесора | 23.0 Вт | 25.8 Вт | на 12% вища |

Методика:

- **3.1 (система):** енергія процесора плюс енергія пам'яті за один запуск. Лічильник `energy-psys` не використано: на цьому ноутбуці
  він показує менше значення, ніж `energy-pkg`, хоча повинен включати процесор, тому йому не можна довіряти.
- **3.2 (лише програма):** від виміряної енергії процесора віднімається те, що система витратила б у простої за той самий час:
  `E_програми = E_pkg - P_простою x t`, де `P_простою = 2.43 Вт`.

Пояснення (п. 4.4): енергія дорівнює потужності, помноженій на час. Середня потужність після оптимізації навіть трохи зросла,
бо векторні блоки AVX2 та FMA завантажують процесор щільніше за скалярний код. Але час роботи скоротився у 15 разів,
тому сумарна енергія зменшилась у 13 разів. Швидше виконати роботу й повернутися в простій вигідніше з точки зору енергії.

Обмеження методики: RAPL не враховує екран та інші компоненти ноутбука, фонове навантаження вважається постійним,
а значення `energy-cores` у простої малі й мають велику відносну похибку.

## 4. Асемблер (п. 4.1, 4.1.1)

    gcc -O0 -S -masm=intel mm.c -o mm0.s
    gcc -O3 -march=native -S -masm=intel mm.c -o mm3.s
    gcc -O3 -march=native -fopt-info-vec mm.c -o /dev/null

Компілятор підтверджує векторизацію (`loop vectorized using 32 byte vectors`). Регістри `ymm` у `mm0.s` зустрічаються 0 разів, у `mm3.s` 24.

| | `-O0` | `-O3 -march=native` |
|---|---|---|
| Інструкцій у внутрішньому циклі | 41 на 1 елемент | 8 на 8 елементів |
| Тип інструкцій | скалярні (`movsd`, `mulsd`, `addsd`) | векторні AVX2 (`vmovapd`, `vfmadd213pd`, `vfmadd231pd`) |
| Регістри | `xmm` (одне число) | `ymm` (256 біт, 4 числа `double`) |
| Змінні `i`, `j`, `k` | у стеку (`[rbp-N]`) | у регістрах |
| Множення та додавання | окремі інструкції | одна FMA-інструкція |
| `A[i][k]` | завантажується на кожній ітерації | винесено з циклу (`vbroadcastsd`) |
| Розрахунок адреси | повторюється 4 рази за ітерацію | зсув вказівників на 32 байти |
| Розгортання циклу | немає | удвічі за `k` |

**SIMD / AVX2 (п. 4.1.1):** `vmovapd` завантажує 4 числа `double` за одну інструкцію. `vfmadd213pd` та `vfmadd231pd` (FMA, fused multiply-add)
виконують множення і додавання разом над 4 числами. Літери `pd` означають packed double, `v` означає VEX/AVX-кодування.
`vbroadcastsd` копіює одне число в усі 4 позиції регістра `ymm`.

Перевірка за числами `perf stat`: `mm0`: 1024^3 ≈ 1.07 млрд ітерацій x 41 інструкція ≈ 44 млрд (виміряно 43.98 млрд).
`mm3`: 1024 x 512 x 256 ≈ 134 млн ітерацій x 8 інструкцій ≈ 1.07 млрд (виміряно 1.11 млрд).
Прискорення (~15 разів) більше за теоретичні 4 рази від SIMD, бо додатково дали ефект змінні в регістрах, FMA та розгортання циклу.

## Загальний висновок

Оптимізація `-O3 -march=native` прискорила програму приблизно в 15 разів, скоротила кількість інструкцій у ~39 разів і зменшила енерговитрати
у ~13 разів. Єдина гаряча точка це функція `multiply`. Оптимізована версія обмежена пропускною здатністю пам'яті,
тому подальше прискорення можливе блочним (tiled) множенням матриць.
